# Process Life Cycle Management Project – Meeting Notes

## Terminology

* Avoid using **"Process Complete"** because completion and termination are not necessarily the same thing.
* "Terminated" may imply forced termination.
* Preferred term: **"Finished Processes"**.
* Remove redundant displays of finished/completed processes if the same information is already visible elsewhere.

---

## State Presence

* State Presence view should show how long each process spends in every state.
* Useful for both visualization and evaluation purposes.
* Feature is acceptable and should be retained.

---

## Evaluation Metrics

* Retain counts for:

  * Valid transitions
  * Invalid transitions
* Invalid transitions should ideally be zero.
* These metrics are useful for assessment and evaluation.

---

## Current Time Display

* Current Time is a display element, not a control.
* Move it to the display section rather than grouping it with controls.
* Maintain a clear distinction between controls and status displays.        

---

## UI Controls and Buttons

* Interactive elements should clearly look clickable.
* Some current buttons do not visually communicate that they are interactive.
* Consider:

  * Better borders
  * Slight elevation/3D appearance
  * Hover effects
  * Subtle size or color changes on hover
* Users should immediately recognize what can be clicked.

---

## Layout and Scrolling

* Page layout should remain fixed.
* Dynamic content should not continuously push other sections down.
* Action logs, histories, and similar sections should be placed inside scrollable containers.
* Individual panels should scroll instead of resizing the entire page.
* Avoid situations where users need to scroll the entire page just to access logs.

---

## Action Log

* Reserve a fixed space for the action log.
* Make the log scrollable.
* Prevent layout shifts as more events are generated.

---

## State Transition History

### Invalid Transition Visualization

* Invalid transitions should not be visible only in logs.
* Display them directly in the state history visualization.
* Possible representations:

  * Cross mark (X)
  * Distinct invalid edge
  * Separate invalid branch

### Graph-Based History

* State history should be represented as a graph rather than a simple sequence.
* Need to show:

  * Valid transitions
  * Invalid attempts
  * Actual process progression

### Per-Process View

* Show one process graph at a time.
* Use tabs (P0, P1, P2, etc.).
* Selecting a process displays its complete history graph.
* This saves space and improves readability.

---

## Information Architecture

* Minimize redundancy.
* Information should appear where users naturally expect to find it.
* Avoid repeating the same information in multiple places.
* Keep sections self-contained whenever possible.

---

## Sandbox Documentation

* Sandbox needs a clear description.
* Users should understand:

  * What the sandbox is
  * Why it exists
  * What can be done in it
* Add a dedicated information/help section.
* Description should explain purpose, not merely repeat controls.

---

## Tooltips and Help Text

### Avoid Imperative Language

Current style is overly command-oriented.

Examples to avoid:

* Create processes
* Move processes
* Advance clock

Prefer descriptive wording:

* Advances the clock by one unit when clicked.
* Allows creation and movement of processes between states.
* Displays process state changes over time.

Goal:

* More user-friendly interface.
* Reduce cognitive pressure and anxiety.
* Improve overall usability.

---

## Sandbox, Scenarios, and Learning Modes

### Sandbox

* Sandbox is essentially an exploration environment.
* Consider renaming to:

  * Explore
  * Exploration
  * Exploratorium (discussion only)

Characteristics:

* No objective
* Free experimentation
* User-driven exploration

---

### Scenarios

Discussion around the word "Scenario".

Concern:

* From a student's perspective, they are performing a task or experiment.
* "Scenario" may be more meaningful from an evaluation perspective than a learner perspective.

Possible alternatives:

* Task
* Assignment
* Experiment

Most preferred option:

* **Experiment**

Examples:

* Experiment 0
* Experiment 1
* Experiment 2

---

## Tutorial vs Experiment

* Scenario 0 functions as an onboarding/tutorial activity.
* Remaining activities should not be described as tutorials.
* Focus should be on what the learner must accomplish rather than on learning outcomes.

---

## Objectives

* Objectives should describe the activity to be performed.
* Avoid objectives such as:

  * Understand process lifecycle
  * Learn process management

Instead use activity-oriented objectives:

* Create a process.
* Move a process through valid states.
* Complete a process lifecycle.
* Handle process events correctly.

Learning is a consequence of performing the activity, not the activity itself.

---

## Event Catalogue

* Need a visible catalogue/reference of lifecycle events.
* Users should be able to see:

  * Available events
  * Meaning of each event
  * Where each event can occur
* Current scenarios reference events that are not clearly documented.

---

## UI/UX Design Feedback

* Need stronger focus on UI/UX principles.
* Team should spend more time studying:

  * User Interface Design
  * Human-Computer Interaction
  * Interaction Design
* Review good UI examples and established design practices.
